# 困难题本地闸门

困难题设计可参考三信号、题面回指、P3 下限、跨边界拓扑和结构合规。首轮草稿只使用已掌握的源码及历史证据，不预先声明模型修改量或虚构历史样本。平台预检结果仍须通过 API 取得。

当前校验器是有 A/B 产物时的辅助审阅工具：它同时检查题面结构和已声明的 A/B 改动，尚未适配单模型首轮出题。具体记录放在一个 JSON 文件，题面单独放在文本文件；A/B 场景本地运行：

```bash
python tools/validate_hard_task.py \
  --review /绝对路径/hard-review.json \
  --prompt /绝对路径/PROMPT.md \
  --difficulty 困难 \
  --verdict pass
```

有 A/B 远端 commit 时再追加 `--repo`、`--base`、`--head-a`、`--head-b`，校验器会用 `git diff --numstat` 重新计算非测试业务代码行数和文件数；不传这些参数时只检查记录中的声明，仍需人工复核远端差异。

校验器会强制：

- `signals` 至少两项通过，且包含关键设计取舍或复杂技术关注点；通过项的模块数、证据和技术风险字段达到最小长度。
- 三项 `platformSignals`、跨对象不变量、历史废弃/通过样本和实质复杂度都能逐字回指题面或带有历史记录 ID。
- 四项 `p3DifficultyFloor`、跨模块架构、仓库上下文依赖和一轮完成反证齐全；题面与自报命中两项时禁止一轮完成。
- `complexityTopology` 使用八类枚举之一，明确两侧状态持有者、各侧独占对象、失败恢复和负面结果。
- `schemaVersion=1`、`difficulty`、`verdict`、`reviewedBy`、`routineOnly=false` 一致；题面不超过 240 字，不能含 Markdown、路径或代码术语，硬性措辞不超过三处。
- 有 A/B 的收集场景建议每份改动至少 30 行非测试业务代码、跨至少三个业务文件。此工具将该建议作为辅助审阅门槛并要求 commit 声明，不能把它当成所有单模型任务的硬性条件。

“历史记录 ID”只证明材料可追溯，不自动证明内容真实；公开语料、远端 commit 和实际差异仍要在提交前人工复核。校验器只读本地文件，不调用平台、不提交预检、不写平台备注。
