# Prompt 与 Rubric 加固

这份门禁用于出题、历史补建和平台返修。目标是让 Rubric 只验收 Prompt 已经要求的行为，并在预检前证明固定基线还没有等价能力。

## 1. 先写范围合同

题面冻结前建立 `design-contract.json`。它不是给模型执行的材料，而是本地审查记录：

```json
{
  "schema_version": 1,
  "prompt_clauses": [
    {
      "id": "P1",
      "quote": "读取时能返回最新版本",
      "required": true
    }
  ],
  "rubric_map": [
    {
      "id": 1,
      "clause_ids": ["P1"],
      "observable": "调用读取入口后得到的值与数据库最终状态"
    }
  ],
  "novelty": {
    "status": "confirmed",
    "checks": [
      {
        "area": "runtime_behavior",
        "result": "gap_confirmed",
        "evidence": ["baseline-read-returns-old.json"]
      },
      {
        "area": "tests",
        "result": "absent",
        "evidence": ["baseline-test-search.json"]
      }
    ]
  },
  "submission": {
    "phase": "design"
  }
}
```

`quote` 必须逐字来自题面。每个必需条款至少映射一条 Rubric；每条 Rubric 也必须回指至少一个 Prompt 条款。无法说明映射的要求应删除，不能靠“相关维度覆盖”为它补理由。

出题前使用 `submission.phase=design`。design 阶段还必须在合同顶层填写 `depth`（必改位置、停止陷阱、预测轮数、基线健康），格式和判定见 [ROUND_DEPTH_DESIGN.md](ROUND_DEPTH_DESIGN.md)；缺失或不达标时校验器非零退出。正式提交前改成 `final`，并填入真实 `effective_rounds`、`question_type` 和 `requirement_completed`，再带 `--artifact-result` 重跑。

运行：

```bash
python scripts/check_prompt_rubric_scope.py \
  --prompt /绝对路径/PROMPT.md \
  --rubric /绝对路径/rubric.yaml \
  --contract /绝对路径/design-contract.json
```

有产物结果时再传 `--artifact-result /绝对路径/artifact-result.txt`。脚本非零退出即停止预检，不生成交付表。

把 `design-contract.json` 的实际哈希和字节数加入 `design-draft.json` 的 `source_evidence`，让出题设计记录一并快照这份合同；`basis` 写明合同路径和最终结论。

## 2. 新颖性与 R2

“Issue 里没写”“搜索结果没命中”不证明固定基线没有该能力。至少在两个独立面核验，且其中一项必须是真实运行、公开 API 或测试：

- 文档和发布说明是否已经宣传同一能力；
- 路由、命令、配置项和公开 schema 是否已有入口；
- 基线测试是否已经覆盖核心行为；
- 用固定基线和可控夹具实际执行一次，记录观察结果；
- 必要时查提交历史，确认能力的引入时间早于固定基线。

以下情况直接放弃题目，不改成残缺题：

- 跨库原子提交、离线镜像打包这类等价能力已经存在；
- 只有名称或返回文案不同，数据和状态语义相同；
- 只能通过删除既有行为或制造人为退化才形成“缺陷”。

新颖性证据保存到合同里。文件证据使用绝对路径、SHA-256 和字节数；不要把基线研究笔记放进模型源码工作区。

## 3. Rubric 只做需求回指

每条 Rubric 先问三件事：

1. Prompt 中哪一句要求了这个结果？
2. 调用方能从哪个公开入口、状态或最终数据观察到它？
3. 一个同样满足 Prompt、但实现方式不同的版本会不会被误杀？

采用行为边界，不规定实现位置：

- 可以写“在查询数据库前拒绝”，不要写“必须在 resolver 外执行校验”。
- 可以写“客户端收到可定位的 GraphQL 错误”，不要绑定内部错误类型或某一层函数。
- 可以写“服务重启后状态仍可读”，不要指定某个文件名或持久化库。
- 可以写“查询尚未完成时调用方能发出停止请求”，不要写“发起查询时返回一个停止句柄”。返回句柄、调用方预建的事件或令牌、回调、新方法、新参数都是同一能力的不同入口形态；Prompt 没点名入口形态时，Rubric 只验能力是否生效，验收脚本要接受任一形态（2026-10-31 5131 v2 被打回）。

不新增 Prompt 未要求的义务：

| 只在 Prompt 明确出现时保留 | 不能从“方便定位”自动推导 |
|---|---|
| 日志、状态接口、监控 | 额外可观测性接口 |
| 性能、延迟、吞吐、大表、可用性 | “不显著影响性能”这类未量化指标 |
| 重试、重复执行、幂等、去重 | 任意写操作自动幂等 |
| 过滤、筛选、查询条件 | 额外过滤接口 |
| 汇总、聚合、跨节点一致 | 跨节点汇总能力 |
| 取消、中止、半成品清理 | 取消与资源清理流程 |
| 不中断或不阻塞写入 | 实时无锁的一致性检查 |
| 回显输入路径、生成时间、校验和等归档元数据 | 系统读取用户提供的输入 |
| 新的“无法匹配/未知”分类及分类计数 | 用户已经列明的分类结果 |
| 进程退出后的跨运行恢复、持久化事务日志 | 当前执行中途失败要回滚 |
| 用户级/项目级作用域分组与组间隔离 | 一次给多款助手安装本机设置 |
| 由返回的句柄、令牌、回调或特定方法提供某个能力 | 调用方能够发出停止、取消等请求 |
| 文字/机器可读/序列化输出携带终态、行数或计数 | 结果能说清正常结束、停止还是失败 |

Prompt 确实提出性能要求时，写出可观测门槛。例如“在固定夹具和固定并发下，P95 不超过 200 ms”，不要写“不能明显变慢”。

同一能力有多个入口时，分别说明每个入口是否属于 Prompt 范围。不能把未提到的 CLI 或管理接口算作必需。

## 4. 覆盖要完整但不扩张

困难题通常保持 8 至 12 条，但条数只服务覆盖。先列 Prompt 条款，再补相邻回归，不从通用维度表反向生成需求。

建议覆盖顺序：

1. 主流程与每个明确入口；
2. 输入边界和错误结果；
3. 失败回滚、恢复与幂等，仅在 Prompt 要求时；
4. 并发和持久化，仅在需求牵动时；
5. 兼容和不开启新能力时的回归；
6. 安全与权限，仅在存在写操作或敏感数据时。

工具脚本会拦截日志、性能、幂等、过滤、汇总、取消、非阻塞写入、接口形态（停止句柄/令牌/返回对象）、序列化输出新增终态或计数、内部符号和不可量化措辞的常见越界。静态通过仍不能替代人工逐句回指。

## 5. 收录与 Type

提交前以当前平台规则为准。2026-10-21 的实际初检规则明确拒收“有效轮数 <100 且完成状态为完成”的记录，且不受 Type 或长时分类影响。

因此 `<100` 完成样本：

- 可以保留在本地作诊断或对照组；
- 不应提交到正式平台；
- 不能把 `requirement_completed` 改成“部分完成”来绕过；
- 不能修改真实轮数。

`效果差` 必须至少有一个稳定复现的未通过 Rubric，且未通过项落在核心工作流或关键边界。所有 Rubric 通过却标成“效果差”会在初检被拦截。

## 6. 返修分流

平台返回 `PENDING_FIX` 后，先读取 `GET /api/v1/submissions/<id>` 的 `submission.reject_reason` 和 `qc.note`，按四类处理：

| 类型 | 处理 |
|---|---|
| A. 表单/Rubric 映射错误 | 可以修 Rubric、重编号产物结果并 `PUT /submissions/<id>` 返修 |
| B. 模型产物存在实质缺陷 | 回到对应源码工作区修复产品，重新验收，不能只改文字 |
| C. 固定基线已有等价能力 | 题目不成立，终止本题；不要靠删 Rubric 或改 Type 强行通过 |
| D. 收录规则拒绝 | 保留本地记录，不提交；不得伪造完成状态或轮数 |

返修说明写清删除了哪条越界要求、保留了哪些原始范围，以及为什么没有改源码或运行记录。单次平台写请求结果不明时只读查询，不自动重试。

`llm_rubric_scope` 的点名必须逐子句处理。只删除被点名的额外义务，同一 Rubric 中能回指 Prompt 的主行为保留，原编号不无意义重排；如果确实删除整条，再连续重编号并同步产物结果。被删义务不能继续出现在 v2 的失败说明里。先保留 v1 设计、Rubric、验收结果和截图，再修改模型外验收脚本、重新运行并由真实 Terminal 生成 v2 截图；随后使用 `scripts/repair_submission.py` 先 dry-run，再对原 submission id 执行一次 PUT，并回读 `current_version + 1`。不得修改 Prompt、源码、Session 或轨迹来迁就标准。

### 删掉越界条款后“效果差”还成不成立

`<100 且 效果差` 的题，如果被打回的越界条款恰好是唯一未通过项，删掉之后就会全部通过，落到 D 类“`<100` 完成”，不能正式提交。处理顺序：

1. 先把越界条款改成行为中立的写法（或删掉），按改后的文本重跑验收。不能为了维持“效果差”而保留一条本不该失败的条款，平台会查产物与完成度是否自洽。
2. 全部通过时，可以再查一次：其余条款的原文是否本来就覆盖了验收脚本没测到的输入。只能扩大验收输入，不能改条款文本、不能新增条款。扩大的输入必须是 Prompt 没有排除的普通用法（例如同一个查询入口的其他语法形式），不能是专门为了找错而挑的冷门用法。
3. 找到的失败要满足：同一数据上有一个通过的对照（证明探针本身有效），多次运行结果一致，失败只记在原文最直接对应的那一条，不在多条上重复记。修复说明里如实写“v3 扩大了第 N 条的验收输入”，不能写成源码变化或新发现的需求。
4. 找不到这样的失败，就按 D 类处理：保留本地样本，不再返修提交。

2026-10-31 的 5131-rdflib：v2 唯一未通过的是越界的“停止句柄”。改成中立写法后，第 2 条“停止后不再读取存储”加测属性路径查询，发现 `?s ex:p/ex:q ?x` 发出停止请求后还读了 280 次存储、多跑约 0.9 秒，最后标成正常结束；同样数据上的普通模式查询只读 1 次。原因是路径求值在一次取结果内部自己循环读存储，跳过了停止检查。这是第 2 条原文范围内的缺陷，于是保留“部分完成 / 效果差”，未通过项从第 1 条换成第 2 条。

平台检查项全部显示通过但状态仍为 `QC_RUNNING` 时，如实记录“检查结果已出现、终态未落定”，不能自行写成 `QC_PASSED`。

## 7. 实施顺序

1. 研究固定基线和公开 Issue，跑基线构建和全量测试；
2. 在基线上列出必改位置和停止陷阱，登记预测轮数，写入 `depth`；
3. 写 Prompt 条款和排除项，运行 `scripts/check_prompt_style.py`；
4. 完成新颖性证据；
5. 逐条写 Rubric 和条款映射；
6. 运行范围校验器；
7. 人工逐条检查实现中立性、可观察性和收录规则；
8. 通过后再预检、执行和冻结设计。

结果出来后才发现的越界 Rubric 不能静默改写历史设计。新题必须回到设计阶段修正；已提交记录只能按平台返修流程留下版本化说明。
