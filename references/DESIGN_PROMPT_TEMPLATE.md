# 出题标准提示词

## 简短版（只填语言和数量）

```
用 swe-task 技能出 {数量} 道 {语言} 题，只做第一步，不发平台预检。

先完整读一遍 references/DESIGN_PROMPT_TEMPLATE.md 的完整版，并按它执行。项目自己挑：
- 这是新的一批时，先运行 python3 scripts/used_projects.py sync，之前用过的项目全部进排除表，表里的项目一律不用；
- 只接着用本批已选定、还没进排除表的项目（used_projects.py check 显示 matched_by=workflow），且筛查已 PASS、probe.json 里探针题 TraeCN 真实轮数在 110-200、题数还没到 10 道；
- 没有就用 runtime/tools/find_swe_projects.py --language {语言} 找候选，按 PROJECT_SELECTION.md“探针题”一节排先后，逐个跑 screen_project.py --run-container，用第一个 PASS 的。新项目这一批只出 1 道探针题：过完本地门禁和试跑就停下来汇报，由我发预检和 TraeCN，拿到真实轮数后再出剩下的题。

每道题发预检前都要过完五道本地门禁：
- trial_run.py confirm 预演二次确认，不能多出 effect.allowed_new 以外的页面、接口、命令或配置；
- trial_run.py run 试跑不能被熔断（改动源码文件中位数 ≥14，或工具调用超过 400）；
- 换算轮数只作参考；stop_traps 提示“陷阱太浅”就回去换更深的停止陷阱。

一次最多 4 道。数量超过 4 道就分批，每批汇报后停下来，等我确认再继续。同一个项目累计不超过 10 道；当前项目的需求出不够，就说明原因，不要硬凑。
```

---

## 完整版

已经选好项目时，把下面两条分隔线之间的内容整段发给出题模型（Codex 带 swe-task 技能）。花括号里的内容按本批情况替换；不知道的项删掉那一行，模型会在步骤 0 自己找。用简短版时，模型自己读这一节，不用手动发。

---

用 swe-task 技能，为下面这个项目设计一批 SWE 题面，只做第一步“出题与预检前的本地门禁”，不要进入 Trae 执行，也不要发平台预检。

输入：
- 项目：{owner/name}；语言：{Go}
- 基线 commit：{完整 commit，同项目所有题共用；未给则在步骤 0 固定}
- 本批题数：{3} 道（一个项目总共出 8-10 道，本批是第 {1} 批）
- 同批其他草稿：{无 / 名称=路径}
- 项目目录：~/repositories/标注任务/swe/projects/{项目名}/

先读完 SKILL.md、references/PROJECT_SELECTION.md、references/ROUND_DEPTH_DESIGN.md 再动手。

目标是每道题在 TraeCN 上跑 110 到 200 轮：低于 100 平台拒收，超过 200 上下文太长、浪费钱。TraeCN 贵，便宜模型便宜，所以题面在本地用便宜模型试跑过、落在窗口里才算出好。

## 不能做的事

- 不改动、不提交模型将来要用的源码工作区；研究用独立克隆，结束时保持 Git 干净。
- 题面、真实性说明和 Rubric 里不出现任何 Issue/PR 的编号、标题、链接或原句。
- 不靠加功能把题做大，不靠改写措辞绕过功能重合。
- 不发任何平台写请求，不在命令参数或输出里写 Session 令牌。
- 门禁没过不能说“基本通过”；每个结论都要有命令输出或源码行号。

## 步骤 0：项目与基线（项目目录里已有 PASS 报告就跳过）

1. 克隆到 sources/ 下，固定基线 commit。
2. 运行 `scripts/screen_project.py --run-container`，输出到项目目录的 screen-<基线短哈希>/。构建失败先看报告里的 ci_test_commands，按项目自己的 CI 补 --go-tags / --prepare-cmd / --test-cmd 重跑；照 CI 仍失败就停下来报告，不换项目、不硬改。
3. verdict 不是 PASS 就停，报告卡在哪道门禁。

## 步骤 1：Issue 语料与功能索引（每批开始都做）

1. `check_issue_feature_overlap.py fetch` 抓全部 Issue 与 PR，存为项目目录下的 issues-<日期>.json。
2. 项目目录的 issue-features.json 里每条 Issue 写一句“它要什么”（第一批时新建，之后只补新增的），直到 `index` 通过。
3. 读完索引再开始想需求，提前避开已有人提过的方向。

## 步骤 2：在基线上找需求

每道题先回答下面几个问题，写进任务目录的研究笔记，答不上来就换需求：

- 谁在用什么数据、连续做哪几步、结果哪里不对、现在怎么凑合。场景要能在这个项目的真实用户身上发生。
- 基线现在怎么处理：通过公开入口或现有测试实际跑一次，确认新能力确实不存在。
- 必改位置：把诉求落到源码，用 git grep / 调用关系逐个找入口、数据写入与流出点、缓存和持久化，按“相对路径:行号 + 非改不可的原因”记录。少于 12 处、或者分布不到 4 个文件，就换需求；超过 30 处或 10 个文件，收窄或拆成两道。日志、统计、监控、配置开关、单个中间件、单入口批量操作这类改动集中的需求，直接排除。
- 停止陷阱：至少 2 个“看起来做完了其实没做完”的实现，写清它看起来怎样、在本机离线怎么跑出错。
- 用户在哪个现有功能、命令或页面上看到结果，这次要不要新增页面、接口、命令或配置。答不清楚的需求，TraeCN 确认时一定会扩出去。

本批几道题要落在不同的状态和代码路径上，不要同一块逻辑换个说法出两道。

## 步骤 3：功能不重合

每道题用 `skeleton` 生成 overlap-ledger.json，然后逐条填写：
- 本题 feature 一句话，题面 SHA-256。
- 每条 Issue 和每条命中检索词的 PR 的 relation（unrelated / adjacent / overlap）。adjacent 和命中检索词的条目写清分界。
- 同项目每道其他题（脚本自动找已有任务，同批草稿用 --sibling 传）的关系和分界。
- 检索词至少 6 个、英文至少 3 个，要包括同义说法；命中为 0 的词换掉。

出现任何 overlap，包括未合并的 PR 和同批的题，就换掉重合的那部分需求后重新走步骤 2。同批两道重合时留一道、换一道。

## 步骤 4：写题面

写成同事在群里描述自己碰到的麻烦：先说场景和症状，再说想要什么。

- 130 到 220 字，上限 240；纯文本，不分点，不用 Markdown。
- 点名项目里真实的对象和操作（产品名、用户能看到的功能），用具体数字和后果，比如“差了几百块”“月底流量超了”。
- 约束放进场景里写，不要单独列在末段。末段不能只剩“不能、不要”这类句子。
- 不出现文件名、函数名、配置键、类名、斜杠，也不出现 API、JSON、HTTP、HTTPS、SQL、Go、Docker、commit、token、endpoint、schema、CLI、SDK；换成“拉镜像”“令牌”“接口”这类说法。
- “必须、不得、需要、应当、务必、至少、不能、不可、禁止”合计最多 3 处，注意“需要”也算；分号最多 2 个。
- 顿号清单最多一处、最多 3 项；“希望”最多出现一次。不用“明确区分、不受影响、可复核、平滑、干净关闭、互相串、闭环、一致性、确保、保障”这类规格腔。
- 不写“我想”“请帮我”之类的请求套语。
- 用一句同事口吻的话交代效果落在哪、这次做到哪为止，提前答掉 TraeCN 二次确认时会问的“要不要实现对应的接口、页面和测试”。例如“扫完在原来的结果里多列一栏就行”“权限先在代码里配，不用做管理界面”“报表服务那边我们自己接，查询这一层能停下来就够了”。不写“不得新增页面”“范围仅限于”这类条款。

写完自己读一遍：放到别的项目也成立的句子，换成这个项目才有的对象。

## 步骤 5：Rubric 与合同

- Rubric 8 到 12 条，type 只写 f2p / p2p，至少 1 条 f2p。每条都能回指题面里逐字摘出的一句（症状句也可以当锚点），题面没要求的不写。
- 题面没提但修改必然牵动的既有行为，用 p2p 守住。
- 停止陷阱要有对应的 Rubric，能在本机离线验证。
- design-contract.json 写 phase=design；depth 里写必改位置、停止陷阱、预测轮数，以及 baseline_health（从筛查报告原样复制）；effect 里写 seen_in、quote（题面里交代效果落点的那句原文）和 allowed_new。预测轮数先填试跑前的估计，试跑后改成 trial-run.json 里的 prediction.band。

## 步骤 6：便宜模型试跑

四道静态门禁（独立、重合、文风、范围与深度）单独跑通后，按 references/ROUND_DEPTH_DESIGN.md 第 6 节在 ~/repositories/标注任务/swe/trials/<编号>-<项目>/ 下试跑：
1. `trial_run.py confirm`：预演二次确认。模型列出了 effect.allowed_new 之外的页面、接口、命令或配置，回步骤 4 改效果落点那句话。
2. `trial_run.py run --runs 2`（默认自适应，第一次结果明确时只跑一次）：被熔断（改动源码文件中位数 ≥14 或工具调用超限）就缩小需求重来；换算轮数现在是 `breaker_only` 档，只作参考，汇报里写明换算值、两次试跑的工具调用数，以及和同项目已执行题的对比。同一项目连续两道被熔断就停下来报告，建议换项目。off_contract_source_files 非空时对照 confirm 结果改题面。`stop_traps` 有提示时：没有一个陷阱 hit_then_fixed，回步骤 3 换更深的陷阱；某个陷阱每次都 missed，在题面或本地测试里给一点线索。
题面改了任何一个字，两项都要重跑。试跑目录里的代码和日志不能拷进 sources/ 下的任何工作区。

## 步骤 7：本地门禁，全部零退出

每道题运行 `scripts/precheck_gate.py --task-dir <任务目录> --repo <owner/name> --corpus <语料> --features <功能索引> --source <基线源码树>`，同批草稿用 --sibling 传。它依次跑文本独立、功能重合、文风、范围与深度、试跑结果五道门禁，写出 precheck-gate.json；没有这份回执，swe-flow 不会发预检。任何一项非零就回到对应步骤修改需求，不能只改措辞。

## 交付与汇报

每道题的任务目录里放：PROMPT.md、rubric.yaml、design-contract.json、overlap-ledger.json、研究笔记、precheck-gate.json 和 precheck-gate-logs/。

最后用中文汇报，每道题包括：
- 题面全文和字数
- 一句话需求、预测轮数区间
- 必改位置的文件分布（文件数、处数）和两个停止陷阱
- 效果落点那句原文；二次确认预演里模型打算新增什么、想问什么
- 两次试跑的工具调用数、时长、换算出的 TraeCN 轮数区间和 verdict
- 和哪些 Issue、PR、同项目题是 adjacent，分界各一句
- 五道门禁的结果

再列出本批放弃的需求和原因。然后停下来等我确认，确认后才进入平台预检。

## 预检被打回时

按 references/PRECHECK_REJECTION.md 处理：先运行 precheck-status 取证，读 precheck-results 里的打回原文并分类，然后把原文、分类和打算怎么改发给我，等我确认后再返修、重跑或申诉。每条最多返修 2 次。打回暴露出门禁漏洞时，同批、同项目还没执行的题都重新跑一遍 precheck_gate.py。

## 使用说明

- 每批都发一次。第二批开始，“同批其他草稿”只写本批的；前几批的题已经在 workflow 里，脚本会自动找到。
- 汇报里最值得看的是“放弃的需求和原因”。如果放弃的全是因为功能重合，说明这个项目的需求空间快用完了，应该准备换项目。
- 平台预检通过后才进入第二步正式执行。冻结的题面只输入 Trae 一次。
