# 预检被打回的处理

预检属于第一步。被打回的题不能进第二步正式执行。处理原则是先找到打回原因，再动题面；改措辞绕过检查不算修复。

## 1. 先取证

```bash
runtime/bin/swe-flow precheck-status -state <任务目录>/task-state.json
```

读到终态（通过、拒绝、失败）时，平台详情会写进 `<任务目录>/precheck-results/<编号>-<更新时间>.json`。文件内容包括：

- `reject_kind`、`reject_label`、`reject_detail`：打回类型和平台给的原因；
- `issue_dup`：和哪条 Issue 重复；`local_dup`：和平台上哪道已有题重复；
- `difficulty_total` 与 `difficulty_scores`：难度总分与各维度分；
- `rerunnable`、`appealable`：能否返修、能否申诉；`appeals`：申诉记录。

文件权限 0600，不含题面原文。同一次判定重复读取不会产生新文件；返修后再次判定会按新的更新时间另存一份，历次结果都保留下来。不要手工编辑这些文件。

## 2. 分类处理

先看 `reject_label` 和 `reject_detail` 的原文，再对下表归类。平台的类型名以实际文件为准；遇到表里没有的类型，按原文判断属于哪一行，并在第 4 节记录。

| 情况 | 怎么判断 | 处理 |
|---|---|---|
| 系统故障 | 状态是 `PRECHECK_FAILED`，或原因是超时、服务错误，没有给出判定 | `precheck-rerun` 原样重跑一次，再失败就停下来报告 |
| 与 Issue 重复 | `issue_dup` 非空 | 对照本题 `overlap-ledger.json` 里那条 Issue。我们标了 `adjacent` 且分界站得住：申诉一次，理由用台账里的分界。我们漏了或分错了：说明功能重合门禁失守，按第 3 节换需求，并把漏掉的说法补进检索词 |
| 与已有题重复 | `local_dup` 非空 | 撞到同项目自己的题：同项目比对失守，换掉后出的那道。撞到平台上别人的题：本地看不到全库，把对方的一句话需求记进项目目录的 `platform-dups.json`，以后同项目每道题都和它比，然后换需求 |
| 难度不足 | 难度分偏低，或原因指向难度 | 看哪一维低。设计本身够深（必改位置、停止陷阱都在合同里），只是题面没写出来：把跨模块的约束和陷阱写进症状句后返修。设计本身就浅：放弃这道题，不靠堆功能凑难度 |
| 格式、长度、用词 | 原因指向字数、术语、Markdown、硬性措辞 | 本地门禁本该拦住。先补门禁（`check_prompt_style.py` 或 `validate_hard_task.py` 的规则），再改题面 |
| 判断错误 | 原因和题面事实不符 | 申诉一次，理由引用题面原句和基线证据，平台要求至少 10 个字 |

判 `adjacent` 时先按 [PROJECT_SELECTION.md](PROJECT_SELECTION.md) 的 A+B 规则核对。核心对象和生命周期阶段都相同，只是新题多了来源、预览、回滚、幂等或报告等 C 能力，仍属于 `overlap`，不要申诉。

难度分参考：2026-10 缓存里 32 道通过的题，难度总分在 12 到 20 之间。其中 30 道 14 分以上，标“困难”或“地狱”；12 分那道标“适中”，也通过了。被打回的题分数如果明显低于这个区间，先按“难度不足”处理。

## 3. 返修的规矩

- **优先返修原条目。** `precheck-repair` 在原条目上改题面并重新检测，对应页面上的“保存并重新检测”。新建条目要占预检配额，而且会在平台上留下两道相近的题。只有 `rerunnable=true` 时才能返修。
- **改完重跑四道门禁。** 题面、Rubric、合同、台账改完后运行 `scripts/precheck_gate.py`。`precheck-repair` 和 `precheck-submit` 会检查任务目录里的 `precheck-gate.json`：回执必须是这份题面的、四道门禁全部零退出、门禁读过的文件此后没有改过，否则拒绝发送。原样重跑 `precheck-rerun` 不改题面，不需要回执。
- **每条最多返修 2 次。** 第 3 次还被打回就放弃这个需求，把任务标为放弃并写明原因。反复调措辞，最后得到的只会是一份专门对付检查器的题面。
- **申诉只用于有证据的误判，每条一次。** `swe-flow` 没有申诉命令，申诉在平台页面上做。申诉和返修是两条流程，不要同时进行。
- **每次平台写操作都要用户确认。** 返修、重跑、申诉都带 `-execute` 或在页面操作，执行前把打回原文、分类、打算怎么改发给用户。
- **一道题被打回，牵连同项目的其他题。** 打回暴露的是门禁漏洞时（漏了同义词、漏比了某道题），用补过的检索词把同批、同项目所有还没执行的题重新跑一遍 `precheck_gate.py`，发现重合的一起处理，不等平台逐个打回。

## 4. 记录

每次打回都在项目目录 `~/repositories/标注任务/swe/projects/<项目名>/rejections.jsonl` 追加一行：

```json
{"task": "3390-xxx", "item_id": 3390, "attempt": 1, "reject_kind": "ISSUE_DUP", "reject_label": "…", "category": "与 Issue 重复", "gate_missed": "feature_overlap", "action": "repair", "change": "去掉登录，身份改为现有访问令牌", "result_file": "precheck-results/3390-….json", "outcome": "passed"}
```

`gate_missed` 写本该拦住这次打回的本地门禁（`independence`、`feature_overlap`、`style`、`scope_depth`，或 `none` 表示平台误判）。积累几次之后，哪道门禁最常漏一眼就能看出来，就先改那道门禁。

## 5. 同批题怎么继续

一道题被打回不影响同批其他题的预检，也不影响已通过题进入第二步。只有本节第 3 条“牵连”的情况，才需要回头重查同批的题。
